## 当前需要处理的问题

### 1. 合同询价的空 JSON 对象类型验证不完整

位置：`app/api/data/contract-analysis/route.ts` 的 POST 入口。

请求 JSON 为 `null` 时，代码读取 `body.text` 抛异常。隔离调用复现，线上只读询价请求也确认返回空响应 500；普通 `{}` 返回的是带解释的 400。

建议：先校验请求必须是对象、`text` 必须是字符串；无效输入统一返回 400 和说明，避免用户无反馈。

### 2. 无收单时，LP 接口与页面的比例口径不同

位置：`app/api/data/offers/route.ts` 的 `lp_ratio` SQL，与 `app/page.tsx` 的 `calculate`。

全量检查中 3,994 个无收单方案，接口仍返回负的 `lp_ratio`，但 `min_profit` 为 null。比如军团 1000002、方案 4501、物品 13241，接口比例为 -1000。页面重新计算后将该比例按 0 处理，并且不会将无收单方案用于盈利组合。

影响：当前页面有防护，并非已证明的页面利润错误；接口的调用方却会获得不同口径，接口排序也可能不同于页面排序。建议统一无收单语义和缺价状态，而非把“无法成交”表达成确定亏损。

另有 1,337 个可见方案缺至少一种材料卖价，这是市场缺价计数，不等于数据库损坏。单次组合候选有材料完整性检查；本轮没有对所有脑插套装的特殊计算路径执行缺材料价格注入测试。

## 暂缓事项及规则差异

- 用户已排除的累计深度：组合只检查单次覆盖，未扣减多次/共享物品的累计深度。真实组合函数的隔离案例中，买单仅够 1 件仍推荐 10 次。此次不改。
- 重复物品合并可以超过 JavaScript 安全整数；非法数量行会被解析器忽略。属于数量相关边界，按本轮范围暂缓。
- 当前脑插套装估值优先收单、缺失时用历史价；仓库 AGENTS 中仍写卖单优先。页面和实现一致，但文档规则不一致。本轮保留既有业务，不擅自改为卖单。
