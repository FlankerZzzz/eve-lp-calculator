# 数据库新结构设计记录

记录日期：2026-10-10。本文保留早期设计讨论，不代表当前部署状态。V2.0 正式运行边界、就绪校验与清理流程以 [v2-production.md](v2-production.md) 为准；后续规则覆盖早期讨论。

## 开发边界

- 新旧两条开发线并行：现有服务继续使用现有表；新结构独立设计和验证。
- 不修改、删除、重命名现有服务表，不调整现有服务的数据读写路径。
- 后续新结构实现必须使用独立数据库或明确隔离的存储，具体方案待确认。
- 本次仅整理文档，不重启容器、不发布、不修改数据库。

以上是早期设计阶段边界；用户随后授权建立独立 V2 数据库、触发同步并准备业务切换，仍未授权跳过人工验收删除旧库。

## 业务模块

1. 物品全量及蓝图制造资料。
2. LP 兑换资料，包含势力、军团、兑换方案、材料和脑插套装组合。
3. 订单全量。
4. 合同全量及物品明细。
5. 历史成交。

以上是业务模块，不要求恰好五张物理表。

## 物品主表

| 字段 | 含义与规则 |
| --- | --- |
| type_id | 物品 ID，主键 |
| name_zh | 中文名称 |
| name_en | 英文名称 |
| group_id | 物品分组 ID，沿用现有资料 |
| volume | 单位体积；舰船为整船体积 |
| packaged_volume | 装箱体积；不适用或未知时为空 |
| blueprint_id | 对应制造蓝图 ID；按一个物品一个制造方案设计，未关联时为空 |
| in_serenity_catalog | 是否出现在晨曦 ESI 全量物品 ID 名单中，只写 Y / N |
| source | SDE 已有物品写 SDE，通过 ESI 补入的物品写 ESI |
| published | 来源数据的发布标记；不等于存在市场订单 |
| updated_at | 基础资料更新时间 |

分类字段讨论记录：category_id 有分类用途，market_group_id 当前没有明确业务需求；两者是否实际纳入需最终确认，不在实现时自行添加。

本轮用户明确不增加 portion_size、mass、capacity、description_zh、source_version。不因未来工业模块的假设需求自行扩展字段。

不在主表保存订单价格、合同数量、总体积、历史成交数据、同步任务进度或蓝图材料清单。

## 获取流程

1. 导入标准 SDE，建立物品主表。
2. 获取晨曦 ESI `/universe/types/` 的全量物品 ID 名单。
3. 对比名单与主表，找出 ESI 有、主表没有的 ID。
4. 仅对缺失 ID 请求 ESI 物品详情，补入主表。
5. SDE 有但晨曦名单没有的物品保留，in_serenity_catalog 写 N，不自动删除。

体积是物品主表字段，不再独立维护体积表或体积同步按钮。SDE 导入和缺失 ID 的 ESI 详情补入时一并保存体积。这里取消的是新结构独立任务，现有服务的体积表和按钮不修改。详情失败或字段缺失不能视为补全成功；已有 ID 的字段缺失仍属于后续更新策略，不自动扩大请求范围。

市场订单表和 LP 表不参与物品主表的覆盖范围判断。已有物品字段缺失和版本变化的更新规则另行设计；不把本次缺失 ID 补全解释为全面字段更新。

ESI 物品详情补全不提供完整制造配方。蓝图制造关系与材料从 SDE 导入；资料缺失不得直接解释为不可制造。

## 蓝图关联

- 用户明确按一个物品对应一个蓝图制造方案设计，不考虑多方案。
- 蓝图材料独立于物品主表保存。
- blueprint_id 为空只表示尚未建立制造关联，不直接判定不可制造。

### 已确认：采用两张表

材料在数据库中按行保存，不在蓝图表中存材料 JSON。接口读取时可组合返回一张蓝图及其完整材料 JSON 数组。

蓝图制造表建议字段：

| 字段 | 含义 |
| --- | --- |
| blueprint_id | 蓝图物品 ID，主键，关联物品主表 |
| product_type_id | 产物物品 ID，唯一，关联物品主表 |
| product_quantity | 单次制造产出数量 |
| manufacturing_time | 基础制造时间，秒 |
| updated_at | 更新时间 |

蓝图材料表建议字段：

| 字段 | 含义 |
| --- | --- |
| blueprint_id | 蓝图 ID，关联蓝图制造表 |
| material_type_id | 材料物品 ID，关联物品主表 |
| quantity | 单次制造的基础材料数量 |

- 蓝图材料表以 `(blueprint_id, material_type_id)` 为联合主键。
- 为 material_type_id 建索引，支持反查一种材料被哪些蓝图使用。
- 只保存实际配方材料，不生成物品与材料的笛卡尔积，不重复保存材料名称、体积或价格。
- 制造次数、材料效率和设施等修正属于计算逻辑，不改变基础配方数量。
- 物品主表 blueprint_id 与制造表的产物关联应在导入时保持一致；具体导入、校验和事务规则待设计。
- 两张表的方案已确认；本次仍只记录设计，不创建表或迁移现有数据。

## LP 兑换数据：已确认两张表

LP 关联与兑换方案合并为一张 LP 兑换表，一条兑换方案一行。

| 字段 | 含义 |
| --- | --- |
| faction_id | 势力 ID |
| faction_name_zh | 势力中文名 |
| faction_name_en | 势力英文名 |
| corporation_id | 军团 ID |
| corporation_name_zh | 军团中文名 |
| corporation_name_en | 军团英文名 |
| offer_id | 接口返回的兑换方案 ID |
| type_id | 产出物品 ID，关联物品主表 |
| quantity | 一次兑换的产出数量 |
| lp_cost | 一次兑换的 LP 成本 |
| isk_cost | 一次兑换的 ISK 成本 |
| ak_cost | 一次兑换的 AK 成本 |

势力、军团中文和英文名在兑换表保存，更新时保持同一实体的名称一致。物品名称不重复保存，从物品主表读取。

LP 兑换需求材料表与蓝图材料表采用相同的分行结构：一种材料一行。

| 字段 | 含义 |
| --- | --- |
| corporation_id | 军团 ID |
| offer_id | 兑换方案 ID |
| material_type_id | 需求材料物品 ID，关联物品主表 |
| quantity | 一次兑换所需的材料数量 |

- 已核实现有数据中 offer_id 跨军团重复，不能单独作为军团兑换记录的主键。完整关联键采用 `(corporation_id, offer_id)`。
- 材料表相应以 `(corporation_id, offer_id, material_type_id)` 为联合主键，为 material_type_id 建索引以支持反查。
- 材料来源是 LP 商店接口方案中的 required_items；成本与材料都按一次兑换保存，不按单位产物拆分。
- 材料表不重复保存名称、体积、价格，也不把制造材料与兑换需求材料混为一张表。
- 查询时可以组合返回兑换方案及其材料 JSON 数组，数据库仍按行保存。
- 不增加 deco 字段，屏蔽逻辑后续独立设计；此决定不改变现有服务的排除规则。

## 脑插套装：已确认两张小表

脑插属于 LP 数据模块。提前维护套装定义和军团归属，不在每次查询时临时推断归属。

### 脑插套装表

一套一行，套装 ID 由内部维护。

| 字段 | 含义 |
| --- | --- |
| set_id | 套装唯一 ID，主键 |
| name_zh | 套装中文名 |
| name_en | 套装英文名 |
| slot_1_type_id | 第 1 个槽位的脑插物品 ID |
| slot_2_type_id | 第 2 个槽位的脑插物品 ID |
| slot_3_type_id | 第 3 个槽位的脑插物品 ID |
| slot_4_type_id | 第 4 个槽位的脑插物品 ID |
| slot_5_type_id | 第 5 个槽位的脑插物品 ID |
| slot_6_type_id | 第 6 个槽位的脑插物品 ID |

六个组件 ID 关联物品主表，组件名称和体积不重复保存。同一套装供多个军团提供时只维护一份定义。

### 军团脑插套装关联表

| 字段 | 含义 |
| --- | --- |
| faction_id | 势力 ID |
| corporation_id | 军团 ID |
| set_id | 套装 ID，关联脑插套装表 |

- 一个军团提供多个套装时保存多行，不设置 set_id_1、set_id_2 等动态列。
- `(corporation_id, set_id)` 唯一，避免重复关联同一套装。
- 势力与军团归属应与 LP 兑换表一致。
- 提前维护的是套装归属，不是套装成本或价格。
- 计算时以军团 ID 和六个组件物品 ID 匹配 LP 兑换方案，再关联需求材料；成本不在套装表重复保存。
- 维护关联时校验六个组件的兑换方案是否齐全。兑换方案后续变化导致缺件时应提示并停止完整套装成本计算，不输出不完整结果。
- 同一组件存在多个兑换方案时的选择规则尚待确定，不随意选择一条。
- 套装定义还可供合同扫描识别完整六件套使用。
- 本次仅记录设计，不修改现有 implant_catalog 或其他服务表。

## 订单全量：已确认获取范围

- 数据范围为晨曦伏尔戈星域，region_id 为 10000002，不是全服订单，也不局限于吉他单站。
- 请求 `/markets/10000002/orders/?datasource=serenity&order_type=all&page=N`，分页获取买卖双方订单，不限定物品或空间站。
- 采用接口返回的完整订单数据作为新结构原始资料方向；新表字段和约束尚待最终确认。
- 不改变现有订单同步器和现有服务表。

当前实现核对记录：原始订单使用 active/inactive 双槽；新一轮分页写入非活跃槽，完整成功后在事务中切换活跃槽并替换价格汇总和档位数据，提交后清理旧槽。失败或暂停不发布未完成数据，保留上一份有效快照。此处是现有实现说明，不代表已经实现新结构。

### 已确认：完整快照替换

- 新订单表每轮全量获取，完整替换上一轮，不只更新新增订单。
- 拉取期间继续读取上一轮完整快照，新一轮数据写入隔离的暂存区域。
- 所有分页成功并完成必要校验后，原子切换至新快照；若维护派生价格汇总和档位，也须与原始订单快照一致发布。
- 成功切换后清理旧快照，不无限累积每轮订单历史。
- 本轮新增订单进入新快照，价格和剩余数量采用本轮结果；本轮未出现的订单不再属于当前快照。
- 失败或暂停保留上一轮完整快照，不清空有效数据，不向业务发布半份数据。
- 暂存和切换的具体实现方式在新结构开发时确定，不修改现有服务表。

## 合同：已确认范围与原始数据保留

- 获取范围为晨曦伏尔戈星域公开合同，region_id 为 10000002；不扩展至其他星域或私人合同。
- 两类接口数据都保留完整原始 JSON 字段和值，不只保留脑插或蓝图识别所需的字段：
  - 合同列表：`/contracts/public/10000002/?page=N` 返回的合同记录。
  - 合同物品明细：`/contracts/public/items/{contract_id}/` 返回的物品条目。
- 列表与明细通过 contract_id 关联，明细须保留 record_id 等原始字段；不能仅按 type_id 合并条目而丢失蓝图属性或交付方向等差异。
- 后续筛选、估价、套装识别等属于派生业务处理，不覆盖或删减原始数据。
- 原版数据保留指接口原始内容，不等于承诺永久保留每轮历史快照；快照发布、缓存复用及过期清理规则待确认。
- 明细获取覆盖的合同类型、价格条件以及分页处理需要在新结构实现前确认；不把旧实现的正价物品交换过滤自动视为新设计规则。
- 原始 JSON 的落库方式和检索字段尚待设计；本次仅记录，不修改现有合同服务和表。

### 已确认：脑插合同支付筛选

- 核心查询资料为物品 ID、接受方需支付的 ISK、接受方需交付的物品及数量（如有）。合同明细的 is_included 用于区分提供物品与要求交付物品，不能把支付物品当成买到的脑插。
- 脑插合同业务仅接受两类支付方式：
  1. 纯 ISK：有正数 ISK 价格，且不要求交付任何物品。
  2. 纯 PLEX：ISK 价格为 0，仅要求交付 PLEX，且数量为正数；不得同时要求其他物品。
- ISK + 物品（包含 PLEX）、PLEX + 其他物品及其他支付方式不进入正常脑插合同结果；脑插六件套是否完整仍按套装定义单独校验。
- PLEX 支付保存物品 ID 和数量，不预设为 ISK 成本；如需折算，估值口径后续设计。
- 两类属于脑插业务筛选，不是原始合同获取或落库过滤，不能因此删减原始数据。
- 现有合同同步仅拉正价物品交换明细，无法覆盖零 ISK 的纯 PLEX 支付。新结构必须获取这些候选的明细后再判断支付类型，不能沿用 price > 0 的提前过滤。
- 合同索引可随查询需求调整，不改变原始资料；具体索引与 PLEX 类型 ID 的校验在实现阶段确定。

## 历史成交：最终确认维护原始大表

### 原始历史成交表

- 固定查询伏尔戈星域，不在历史成交表保存 region_id；来源范围由同步配置明确。
- 按物品 ID 查询历史接口，查询对象由物品主表提供；具体候选筛选与重查频率待设计。
- 同步时完整保存接口返回的每日原始字段和值，仅补充请求所对应的 type_id，不预先压缩为月度或删减字段。

| 字段 | 含义 |
| --- | --- |
| type_id | 请求对应的物品 ID，关联物品主表 |
| date | 原始成交日期，YYYY-MM-DD |
| average | 原始日均成交价 |
| highest | 原始当日最高成交价 |
| lowest | 原始当日最低成交价 |
| volume | 原始当日成交数量 |
| order_count | 原始当日成交订单数 |

- 一个物品一个交易日期一行，以 `(type_id, date)` 为联合主键。
- 新日期插入，重复日期以接口值更新，不变记录可跳过写入；价格不取整、不保存单位或易读格式文本。
- 请求失败不破坏已有记录，本次未返回的旧日期不自动删除。
- 接口可用日期范围按实际返回处理，不假定固定为 365 天。
- 使用一张长期历史大表，不按日建表。以 `(type_id, date)` 支持物品走势查询，并以 `(date, type_id)` 索引支持按天查询，不建立重复索引。最终存储隔离方式、保留期限和容量验证待实现阶段确定；独立历史库目前仍为建议，不是已执行变更。

- 按天查看直接查询原始表。成交金额、分类汇总、市场指数和联动观察等后续按实际业务设计，暂不增加指标列或计算结果表。

- 本次仅记录设计，不修改当前 market_daily 或在线同步流程。

## 同步规则：新结构重新设计

- 新结构同步按业务模块设计，不沿用现有同步规则；现有服务、表、同步页面和任务保持不动。
- 自动同步模块支持 Cron 定时配置、自动同步开关和手动触发。Cron 可通过页面或后台配置，配置入口具体设计待确认。
- 同一模块关联表应作为一致的数据更新单元，不要求每张物理表独立执行任务。
- 人工维护例外由用户明确指定，不因“所有表支持定时”的早期描述自动增加接口刷新。

- 空间站映射保持人工维护；新映射表字段尚待确认。
- 上述资料不参与自动接口同步，不定时覆盖人工内容，也不把手动编辑或导入等同于接口重新同步。
- 人工维护的编辑、导入导出及校验功能后续设计；不在本次记录中改变现有功能。

- 定时触发不能并发启动同一模块的重复任务；运行中的任务超过计划间隔时不叠加重复扫描，具体跳过/合并调度规则待设计。
- 合同只保留新结构需要的原始获取规则，不在获取明细前用正 ISK 价格排除纯 PLEX 支付合同。
- 历史任务每天运行一次，重试和补跑不应产生重复日成交记录；接口刷新时刻与默认运行时刻在实现前核实。

### 统一接口请求组件

完整技术设计见 [新结构统一同步请求层设计](sync-request-layer-v2.md)。由开发者负责设计；第一版采用单一出站请求池、固定并发槽、均匀发起速率、公共限流冷却与有限重试，不引入复杂的自动扩缩容算法。

新结构所有接口任务复用该组件；模块负责断点和完整数据发布。人工维护表不加入自动请求。本文与请求层文档均为设计记录，不改动旧服务。

### 自动计划配置：用户补充确认

- 同步页面必须提供每个自动同步模块的自动开关。
- 支持 Cron 格式配置；可同时提供可视化选项（每 N 分钟、每天几点、自定义），具体 UI 由开发者设计。
- 可视化与 Cron 使用同一份计划，可视化选项转换成 Cron，不能形成两套互相冲突的定时任务。
- 显示时区 Asia/Shanghai、计划说明和下次运行时间；复杂 Cron 无法回显为简单选项时保留为自定义模式，不自动改写。
- 关闭自动不阻止手动触发。导入导出不属于自动同步任务。

### 手动导入导出：用户新增需求

- 所有非自维护表都须支持手动导出和导入，以便修复数据。
- 自维护表暂不纳入本轮导入导出要求；相关人工维护能力后续单独确认，不删除现有能力。
- 以下为开发者建议的安全设计，尚未实施：
  - 使用带表/模块标识、格式版本和字段定义的结构化导出包，保留完整数据；不把显示用的易读文字当原始数值。
  - 小表可辅以 CSV 编辑；大表支持范围导出、流式读写和后台导入，不一次加载进浏览器或内存；涉及合同完整字段的资料需保留嵌套结构。
  - 导入先暂存与校验，提供新增/更新/错误预览，不直接覆盖在线数据，不接受任意 SQL 文件执行。
  - 校验主键重复、引用 ID、类型、数量、日期、JSON 和关联一致性。数据冲突需明确报告，不悄悄按最后一行覆盖。
  - 默认按主键合并，不因文件缺少记录就删除数据库内容。整模块替换必须独立确认，并保护相关联表。
  - LP 方案与材料、蓝图与材料、合同列表与明细等支持一致的模块修复包；单表修复也必须通过关联检查。
  - 导入与同模块同步互斥，防止旧运行中的同步结果覆盖新导入；提交前备份受影响记录，分阶段校验，正式发布采用事务或快照切换。
  - 大范围导入不能用一个无限长事务阻塞业务，应先写隔离区再发布；恢复方式应在发布前可用。
  - 入口仅允许管理员，限制文件大小和解压规模，记录修复范围及结果，不在日志泄漏敏感信息。
- 人工导入修复是否应被后续同步覆盖，是待用户确认的业务规则；不能默认为永久覆盖或再新增一套人工覆盖表。
- 新线的导入仅作用于新结构，不能开放旧服务数据库的任意表写入。

## SDE 导入：URL 与文件双入口

- 用户确认支持两种入口：通过 URL 下载 SDE，或上传本地 SDE 文件。
- 两种入口共用标准 SDE 的解析、暂存、校验、差异预览与正式发布流程，不分别维护导入逻辑。
- 导入目标为物品主表、蓝图制造表、蓝图材料表，不仅写物品与材料，也建立蓝图到产物的关系。
- SDE 导入只接收 `published=true` 的物品；`published=false` 的物品不写入 V2 主表。标记缺失或类型错误须报错，不得猜测为已发布或未发布。
- 未发布蓝图不导入制造关系；已发布蓝图若产物或材料被未发布规则过滤，也跳过整份配方并记录具体 ID 与原因，避免悬空引用。这是明确的过滤规则，不是静默忽略损坏数据；原始 ID 不存在、数量非法等仍导致导入失败。
- 后续晨曦全量物品同步独立运行，但同样保持已发布物品口径：比较原始 SDE 全 ID，SDE 未发布项不请求 ESI；真正原始 SDE 缺失的 ID 才查询 ESI，且 published=true 才写入。此规则不改动旧数据库、人工保护资料或原始 LP 方案。
- 来源中的物品字段与制造活动、产物、材料按新结构映射；所需产物和材料 ID 要能在物品主表关联。其他制造活动不擅自扩展为当前已确认的制造方案。
- 先解析至隔离暂存区，校验 ID 引用、唯一制造关系、字段与数量；出现多方案冲突或引用缺失时报告，不随意覆盖或删除。
- 正式发布先保证物品资料存在，再处理制造关系与材料；按一致的数据版本发布。导入失败不得让在线查询看到半份资料。
- 未受保护资料按导入范围更新，受保护的物品或完整配方跳过并报告；保护范围及相关引用仍须通过一致性检查。
- 主表保留既有 ESI 补入物品，不因本次 SDE 文件没有这些 ID 就删除。in_serenity_catalog 由晨曦全量 ID 比较决定，不能由 SDE 导入擅自置 Y。
- 后续由用户独立触发物品主表 Sync，执行晨曦全量 ID 比较并为缺失 ID 查询详情，补入主表；体积随资料入库，不另设体积任务。SDE 导入本身不自动触发此流程。
- URL 入口需限制来源、重定向、下载大小和超时，防止任意内网请求；文件入口需校验实际格式并限制解压大小、防止路径穿越。详细允许格式与来源名单在实现前确定。
- 本次仅记录设计，不下载或导入实际 SDE，不修改现有表。

## SDE 与主表 Sync 的执行边界及日志：用户补充确认

- SDE 导入只执行所要求的导入流程，错误忠实报告；不静默跳过坏数据、不猜测修复、不自动改用其他 SDE 或触发 ESI 查询。
- 导入失败不发布不完整资料，不清除旧有效资料、不改变保护标记。错误记录具体阶段、文件/字段/ID 和原因。
- 用户触发主表 Sync 后先核对成功导入的 SDE 基线与主表，再取得完整晨曦 ID 名单，比较缺失 ID 并查询详情补入。
- 该动作不自动重新下载或导入 SDE。无有效 SDE 基线时明确提示先导入；名单分页失败不得把未读取到的 ID 误标为 N。
- 已补入的 ESI 物品不重复查询。普通业务查询只读本地大表，不暗中补查；模块导入中的补齐须显式记录阶段。
- 每个同步模块有独立日志，SDE 导入单独分类；带运行 ID，支持按模块、运行、级别和阶段查询。
- INFO 包含进度、比较数量、增改/保护跳过数量、重试与冷却、发布结果、错误和摘要。失败不能只记录在 DEBUG。
- DEBUG 展示全部业务响应、差集和逐条处理数据，不只打印部分示例；凭据、管理口令、授权头和敏感信息除外。
- 大响应分块或以完整附件保存，页面分页查看，不一次装入内存，不静默截断；通过运行 ID 关联完整内容。
- DEBUG 默认关闭，按模块或运行启用。配置轮转与保留期限，清理规则显式展示，不无限增长。
- 独立模块日志使用统一机制隔离，不要求每个模块新增业务日志表。
- 本次仍只记录设计，不修改现有服务。
