# 新结构统一同步请求层设计

日期：2026-10-10。状态：设计稿，用户授权由开发者设计；未实现、未切换现有服务。

## 1. 目标与边界

- 目标：稳定、避免无效请求、合理利用允许的吞吐量，规则少且可测试。不承诺绝不限流。
- 所有新结构同步模块使用同一个公共请求组件，不各自实现并发、等待和 HTTP 重试。
- 新旧开发线隔离；不修改旧服务的表、请求器、任务和页面。
- 新线试运行必须错开旧线高请求时段或降低新线预算。新请求池无法控制旧进程的请求，不能把新池限额误认为整台服务器的总请求限额。
- 此文件规定请求与调度的技术规则，不授权迁移、删除数据、重启容器或发布。

## 2. 责任分层

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 调度器 | Cron、自动开关、手动触发、模块互斥、运行记录 | 不自己重试 HTTP 请求 |
| 模块任务 | 查询对象、分页、断点、数据校验、事务入库、发布完整快照 | 不直接 fetch，不自己实现并发和退避 |
| 公共请求组件 | 请求队列、并发、发起速率、超时、限流冷却、有限重试、取消、请求日志 | 不筛选业务物品，不将旧数据冒充新成功，不写业务表 |

请求入口示意：`requestJson({ source, path, method, query, body, module, runId, signal, retrySafe })`。
成功返回解析后的完整 JSON 和必要的响应元数据；HTTP 失败、取消、格式失败返回可区分的错误类型。
原始字段不删减或业务改写；原始响应和查询索引投影的存储方式属于落库设计，不由请求层擅自决定。

## 3. 请求池：简单固定槽位，不做复杂自动扩缩容

- 新线第一版由一个同步后台进程拥有出站请求池；模块只是它的任务，不独立建立进程内池。后续若拆多进程，必须先实现共享请求协调，不能复制池后声称限额仍全局有效。
- 同一来源共享并发与速率预算；ESI 与其他外部来源分开，避免一个来源故障阻塞所有来源。
- 全部初次请求和重试都进入同一队列、同样计入预算。
- 固定槽位：完成一条即补下一条，不采用批次屏障等最慢请求，也不需要复杂的滑动时间窗口算法。
- 起步配置：ESI 最多 8 条在途请求，每秒最多启动 5 次（均匀间隔至少 200ms，不允许启动突发）。这些是可调整的客户端试运行参数，不是接口官方额度。
- 稀疏公平派发：按有待请求的模块轮流取一条，模块内部 FIFO；历史的巨大队列不能完全挤占订单。默认不设复杂权重。
- 待请求任务按需产生，队列有界；默认最多挂起 128 条，队列满时上游等待，不一次构造几万个 Promise。容量为内部参数，不必暴露为页面设置。
- 响应体读完或请求中断后释放并发槽；等待重试时释放槽位，不能占着槽位睡眠。
- 第一版不根据短时成功率自动提升并发。先观察，再人工调整公共配置，避免维护复杂自适应算法。

## 4. 超时、响应与错误分类

- 单次尝试默认总超时 30 秒，包含响应体读取。取消信号与超时同时生效。
- 网络故障、超时、408、500/502/503/504：可在安全请求范围内重试。
- 420/429：作为限流响应处理；在下一节执行公共冷却后再有限重试。
- 400/401/403：通常不重试；明确上报参数或权限错误。只有来源文档明确标识的临时限制例外才可另行处理，不凭猜测重试所有 403。
- 404：不重试，由模块判断合同失效或资料不存在；不能把所有 404 解释成正常空清单。
- 其他状态：默认终止，不笼统重试所有 5xx（例如不支持的功能）。
- 200 的合法空数组不等于网络失败；模块判断其意义。非空非法 JSON、意外空响应或与协议矛盾的成功响应，可有限重试并上报，不能静默转换为合法空数组。
- 304 只有存在已验证的对应缓存时才复用；无缓存不把 304 作为空数据。第一版可不启用条件请求，预留对 ETag/Last-Modified 的支持。
- GET 为默认可重试请求；只读查询 POST 需明确标记 retrySafe，例如名称解析。外部有副作用的写请求不得自动套用重试。

## 5. 重试与公共冷却

- 单个逻辑请求最多 4 次尝试：初次 + 3 次重试。
- 普通重试的基础等待依次为 1、2、4 秒，叠加 0～500ms 随机抖动。
- Retry-After 同时支持秒数和 HTTP 日期；等待不得少于有效服务器指示。不得把较长的服务器等待截为 30 秒。
- 识别且验证过的限流/错误预算响应头可用于提前等待；阈值和解析集中在来源适配器，不散落在模块。不能把错误预算当成成功请求速率额度。
- 420/429 默认保守冷却整个 ESI 来源。只有确认来源提供可靠、独立的限流组信息后，才缩小冷却范围；不得由请求路径自行猜组。
- 没有可靠等待信息时，限流冷却从 60 秒开始，连续限流升至 120、240、300 秒；这是客户端回退策略。有效服务器指示仍优先，允许等待超过 300 秒。
- 冷却截止采用现有截止与新截止的较晚值，不能因另一条请求成功而提前解除服务器要求的冷却。
- 冷却期间不派发该来源的新请求或重试；已在途请求允许结束，其返回可延长冷却。
- 连续 5 个传输/超时/可重试服务器错误可触发来源 30 秒故障冷却，避免坏网络下所有队列持续冲击。取消、404 和业务错误不计入；成功传输重置故障计数。服务器明确的等待优先。
- 重试耗尽返回最终错误；任务层保存失败断点，允许恢复。禁止任务层立刻包一层相同 HTTP 重试循环，形成倍增尝试。
- 重试等待、来源冷却和队列等待均可取消；暂停不能等长时间 sleep 结束才生效。

## 6. 模块调度与状态

- 时区统一 Asia/Shanghai。Cron 支持页面或后台配置，存取同一份模块设置；Cron 表达式需校验，不能拼成 shell 命令执行。
- 自动关闭只阻止定时触发，不自动终止当前任务，也不禁止手动执行。
- 暂停当前任务：停止派发，取消在途和等待中的请求，保留已提交断点；不能把取消当作失败重试。
- 恢复沿用断点；重新同步才建立新运行批次。事务提交中的本地写入先安全结束，不粗暴中断数据库事务。
- 同一模块只允许一个有效运行。到点时仍在运行则跳过并记录，不无限积累补跑队列；手动重复点击返回“运行中”。
- 服务恢复后，如该模块错过计划且尚无有效运行，可补跑一次，不逐次补跑所有错过的周期。
- 不同模块允许共享池运行，依赖和发布一致性由任务负责；不能出现读半份订单的新排行榜。排行榜沿用既有计算、过滤、去重与时段逻辑。
- 状态区分 queued/running/retrying/cooling/paused/failed/complete；保留最后成功时间，任务完成不等于本轮全量数据发布成功。

## 7. 模块采用方式

| 模块 | 默认计划 | 获取与发布规则 |
| --- | --- | --- |
| 物品全量 | 手动，自动默认关闭 | SDE 导入后与晨曦全量 ID 比较，仅为缺失 ID 查详情；详情内体积与基础资料一起入主表 |
| 势力/军团/LP | 手动，自动默认关闭 | 获取完整方案及 required_items，成组事务发布；人工脑插资料不覆盖 |
| 订单 | 每 15 分钟 | 伏尔戈完整分页先暂存，全成功后切换，失败保留旧快照 |
| 合同 | 每 30 分钟 | 伏尔戈公开列表刷新，复用有效明细，缺失/失败补拉；不以正 ISK 价格提前排除 PLEX 合同 |
| 历史 | 每天一次，时刻待确认 | 按物品获取原始日记录，每物品事务写入，失败断点恢复；不删除接口未返回的旧日期 |
| 排行榜 | 沿用现有时段和业务逻辑 | 派生计算读取已发布有效数据；不为了新请求层改变收益口径 |
| 脑插、空间站映射 | 人工维护 | 不参加接口自动刷新 |

不设独立体积同步模块、不设独立体积表。物品详情失败或缺少体积时保留缺失状态，不用 0 冒充已补齐；依旧存在的字段缺失及后续字段更新策略另行确认，不能偷偷扩大缺失 ID 查询范围。
SDE 下载、解压、校验、导入是物品模块的本地步骤，不需要与 ESI JSON 请求使用完全相同的传输处理；公共重试和错误策略可复用，但必须流式下载大文件。
SDE 导入与主表 Sync 独立：导入如实报错，不自动补查；触发主表 Sync 后先核对 SDE 基线，再比较完整晨曦 ID 名单并补齐。无有效基线提示先导入，不暗中重新下载 SDE。
合同完整候选类型仍待确认。已确认新一轮完整列表成功发布后立即删除已消失合同及对应明细，不保留旧合同；失败不清理有效旧快照。订单、合同禁止人工导入及保护。

## 8. 配置和日志

- 对外配置优先只提供来源并发上限、每秒发起数、模块 Cron 和自动开关；超时、尝试数和冷却等默认值集中在请求组件，可通过后台高级配置调整，不给每个模块复制一套。
- 调整速率或并发只影响后续派发，不强杀现有请求；响应头等待优先于人工增速。
- 日志统一包含 runId、模块、来源、接口模板、物品/合同或页码标识、尝试次数、耗时、状态码、等待原因和最终结果。
- 各模块独立日志，分 INFO 和 DEBUG。INFO 记录阶段、数量、等待与错误摘要；DEBUG 展示全部业务响应、差集和逐条处理数据，不静默截断。
- 不记录凭据、授权头、管理口令和敏感 URL 参数。大响应分块或保存完整附件，页面分页查看，不一次装入内存；INFO 使用脱敏短摘要，完整业务内容通过运行 ID 关联 DEBUG。
- DEBUG 默认关闭，可按模块/运行启用，明确轮转和保留期限。
- 页面展示队列、在途数、完成/失败数、限流次数、冷却截止和最后错误，不要求用户理解窗口算法。
- 日志与 DEBUG 附件保留一周，统一轮转清理；不因为统一接口增加无限增长的请求日志表。配置、运行与断点的最终存储结构另行确定。

## 9. 验证与交付条件

先通过模拟服务测试，不以反复压真实接口验证限流。

1. 跨模块峰值不超并发上限，启动间隔符合速率预算，重试也计入。
2. 固定槽位持续补位，慢请求不阻塞整批；公平派发且队列不会无限增长。
3. Retry-After 秒数/日期、超长等待、缺失与非法值均有测试；请求失败不会重复等待同一个退避周期。
4. 429/420 使后续派发冷却，普通成功不能提前解除；故障恢复后按配置限速恢复。
5. 400/401/403/404 不错误重试，最多 4 次尝试；只读 POST 与有副作用请求明确区分。
6. 暂停能取消队列、等待和传输，不重试取消，不丢失已提交断点。
7. 任一分页失败不发布半份订单/合同；合法空数组与坏响应区分；历史重跑不产生重复日期。
8. 人工脑插和映射不被同步覆盖，纯 PLEX 合同能进入后续筛选候选。
9. 验证新旧线请求量叠加风险；真实接口仅做低预算验收，并记录有效吞吐、耗时和限流情况后调参。
10. 新组件运行稳定、结果对比通过后另行申请切换，绝不直接替换旧服务。

## 11. V2 初始化提速记录（2026-10-10）

- 用户授权在接口和机器有余量时提高同步负载。本次采样合同请求约 5 次/秒，最近一分钟响应耗时 P95 为 41 毫秒，未记录请求错误、重试或限流冷却。
- 首轮合同明细先保持现有速率直到完整发布，不直接中断其内存暂存阶段；后续历史、晨曦物品补齐以 `V2_REQUEST_RATE=10` 运行，并发上限仍为 8。该值是本次初始化的运行参数，不宣称第三方接口允许固定每秒 10 次。
- 一次性交接工具 `scripts/v2/resume-with-rate.mjs` 校验明确的 V2 初始化进程身份与工作目录，只在合同已完成时停止该进程并恢复未完成模块；历史复用已提交检查点，物品复用已写入资料。不重新运行已完成 LP 和订单任务，不触碰旧服务，不启动第二个重叠请求队列。
- 保留原请求池的超时、重试、420/429 全局冷却和 Retry-After 保护。此次不删除防护，也不修改旧业务的接口负载。
- 交接前若合同失败、暂停或进程提前退出，工具报错停止，不据此标记同步完成或打开业务切换开关。所有剩余任务完成及兼容性检查仍是切换前提。

## 12. 合同持久化断点实现（2026-10-10）

- 首轮合同同步在部分明细返回 HTTP 200 但正文无法解析时失败；之前的内存暂存已随进程退出丢失，不能宣称这些明细可恢复。本次修复从新的请求开始保存，旧服务仍不动。
- 复用已有 `checkpoints` 表，仅增加可空的 JSON `payload` 列，不增加业务表。主键仍是模块、运行 ID、检查点键；既有 LP 和历史的完成标记保留。
- 同一轮目录按 `directory:page:N` 落库；同一合同明细按 `detail:合同ID:page:N` 落库。每个已校验页面的完整响应与完成信息是同一条已提交记录；不采用“只记完成、没有内容”的断点。
- 合同所有明细页完整、记录 ID 不重复后，保存 `detail:合同ID:done`。合法空数组也可完成，404 保存明确的已失效结果；HTTP 200 空正文/损坏 JSON 不能转为空数组或标为成功。
- 单个合同失败会记录合同 ID、接口和原因，其余合同仍尝试并保存成功结果；整轮有未完成明细时任务失败、不发布正式快照。失败记录不是完成标记，下次仍会请求。
- 恢复沿用原运行 ID：已保存目录和明细页不重复请求，完成合同（含合法空明细和明确 404）不重复查询；正在传输但尚未提交的请求可能重试。手动重新同步则产生新运行 ID，不把旧目录混进新轮次。
- 手动恢复经队列入场后仍保留运行 ID；自动计划再次触发失败任务也保留运行 ID，不因重新排队丢弃断点。
- 全部候选完成后，在一个事务内发布合同、明细和派生缓存，立即清理正式列表已不存在的合同，更新快照状态；最后清理合同暂存检查点。任一步失败全部回滚、断点保留。发布已提交但任务状态未更新时，通过正式快照的运行 ID 识别已完成发布，不重复获取。
- V2 SQLite 使用 WAL 与 `synchronous=FULL`，加强提交持久性。旧数据库和旧同步器的持久化设置不修改。
- 已通过模拟测试验证分页失败、新数据库连接恢复、排队恢复、合法空明细、404、原始额外字段保留、发布回滚以及真正 SIGKILL 后恢复。不用反复压真实接口验证故障。
- 历史已经按物品 ID 事务提交数据和检查点，物品补齐已写入的 ID 会复用；订单的逐页断点机制尚未在此修复中补齐，不能宣称所有模块都完成同等粒度的恢复。

## 13. 空明细合同的失效复核（2026-10-10）

- 用户授权核查三份空响应合同，确认无有效数据后放弃。实际检查 `latest`、`v1` 均为 HTTP 200、0 字节正文；刷新完整六页公开目录后，三份合同均已不存在。其中两份已过期，另一份消失的具体业务原因未由接口说明，不能擅自称为撤销或成交。
- 这属于旧暂存目录与当前可访问明细间的时间差，不是已确认的“合同没有物品”。通用 JSON 请求层仍按原规则有限重试，空正文不伪装成 `[]`。
- 只有 HTTP 200 且正文为空导致的明细失败，才触发一次完整公开目录复查；全部分页成功、页数一致、字段及唯一 ID 校验通过后，仅为已不在新目录的失败合同写入 `gone` 检查点，记录原因、复查时间和目录数量。
- 仍在新目录中的空响应合同保持失败；损坏非空 JSON、普通网络错误和未完成的复查目录不得据此舍弃。合法 JSON 空数组仍作为原始空数组处理，明确 404 的原有处理不变。
