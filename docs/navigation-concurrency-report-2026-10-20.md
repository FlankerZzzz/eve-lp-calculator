日期：2026-10-20。测试对象：当前内网部署。首次审计仅测试；随后按用户确认实施修复并发布内网，未触发同步或写入业务数据，未更新公网环境。

## 后续修复与生产构建复测

后续按用户确认实施了[独立计算池和请求保护](jump-compute-pool.md)。以下先记录本地生产构建复测，再记录实际内网发布验收；原始问题证据保留在后文。

- 自动使用最多 4 个计算线程、8 个等待任务；计算前处理及建图在计算线程执行，按服务器快照版本复用基础图结构。
- 进行中相同参数合并；前端同步防重、来源频率与未完成数限额、网关限流／体积限制共同工作。轮换客户端标识不能绕过来源配额。
- 排队／执行／启动均有时限；显式取消、改点、清除、SPA 卸载、整页离开及未取得响应的网络失败会取消订阅，无人等待时终止计算。线程崩溃后可补建。
- 完成后再次核对服务器快照与有效期，不缓存已完成路线，不放宽寻路和安全规则。

已更新 Web 容器并重载网关配置，实际配置为 4 个计算线程、8 个排队任务。同步容器未重启，启动时间保持不变；没有触发同步任务，未发布公网环境。

## 修复前结论

以下为修复前的测试结论与原始证据。

常规导航通过本轮最高 8 个持续计算客户端的短时测试。旗舰自动计算存在 P2 性能问题：同步 CPU 工作占用共享 Web 进程，会让首页、LP 接口和普通导航一起等待。

在 2 个持续计算旗舰路线的客户端下，旗舰计算样本 P95 为 2.95 秒，首页 1.82 秒，LP 详情 2.89 秒。达到预设的旁路响应阈值后停止提高旗舰并发，未执行旗舰 4／8 并发。

三轮低强度交叉实验进一步确认：只启动一个正常的旗舰三点计算，随后到来的普通导航就从约 20–40 毫秒变为等待 1.56–2.06 秒；普通导航自身算法计时仍约 9 毫秒。不是必须很多人同时操作才会出现影响。

建议在旗舰自动计算面向公众正式开放前，先隔离计算工作并增加有界并发控制。不能仅凭当前功能测试通过，就认定并发上线条件也通过。

## 方法和安全边界

- 测试机可用 8 个逻辑 CPU、约 7.7 GiB 内存；结论仅针对这次内网实例，不代表未来公网服务器容量。
- 基线先测空闲服务，再测试常规计算并发 1／4／8、旗舰计算并发 1／2，并测试单客户端交替计算常规／旗舰，最后观察恢复。
- 计算客户端采用闭环请求：一次响应后等待 100 毫秒再发下一次。这比正常用户偶尔点击计算密集；“并发 2”指两个持续计算客户端，不等于系统只能容纳两个在线用户。
- 每阶段设置 8–12 秒目标窗口、请求数上限和最大 8 个计算连接。常规 8 并发阶段在达到 256 次请求后提前结束，约 6.8 秒。
- 约每 600 毫秒轮流探测首页、LP 选项、10 条方案的企业详情、入侵缓存接口；同一探测未完成时不重复发送。没有执行同步／管理写接口。
- 预设停止升压条件：任一旁路接口样本 P95 同时超过 2.5 秒及其空闲基线 5 倍；另有请求超时、服务错误、内存和宿主可用内存的硬停止保护。
- 正式阶梯脚本总耗时约 94 秒，完成 574 次阶段内导航计算、129 次旁路探测，另有 8 次导航预热。随后追加三轮低强度交叉实验。
- 所有阶段内计算均返回成功的 HTTP 响应，完整或部分可达结果与预热结果一致；0 超时、0 HTTP 错误、0 搜索预算拒绝、0 非预期结果差异。完整可达与合法不可达前缀分别作为基线，未把不可达误算成接口故障。

## 交叉复现：一个旗舰计算拖慢普通导航

计算旗舰路线 `8CIX-S → RV5-TT → Asabona`，使用游牧者、三项技能 V、默认入侵规避、关闭 NPC 站过滤。发送旗舰计算后约 150 毫秒，同时发送吉他 → 艾玛的常规三策略计算和首页请求。

控制组：没有旗舰计算时，三次常规响应为 43／21／22 毫秒，首页为 22／21／20 毫秒。

## 原因与影响

- 当前运行结构为一个 Web 服务进程承载页面及计算接口。
- `app/api/navigation/jump/auto/route.ts` 在处理请求时直接调用 `automaticJumpPlan`，没有把计算提交到独立线程／进程。旗舰请求的目录校验、图构造及寻路均含同步 CPU 工作；本轮没有逐函数 CPU 剖析，不将所有耗时都归于单个函数。
- `lib/jump-auto-planner.mjs` 的每段 2 秒／十万状态保护限制的是单段搜索，并非整个 HTTP 请求从到达到返回的排队时限，也不能保证其他请求及时执行。
- 现有相关路由和代理配置没有专门针对旗舰计算的有界任务队列或计算并发隔离。
- 因此增加请求连接并不会让这些 CPU 工作自动并行；其他依赖同一进程的接口可能一起延迟。浏览器里已经加载的地图渲染／本地小工具不等于服务器任务，不应把本次结果解释为所有前端动画都会冻结。

本轮未出现算错、超时、进程退出或 OOM。资源采样中 Web 容器内存最高约 594 MiB，宿主可用内存最低约 4.9 GiB，没有内存逼近上限的迹象。Docker CPU 采样峰值约 136%，按容器口径约为 1.36 个逻辑 CPU 的用量，并非整台 8 核机器耗尽。

停压后服务健康正常，容器进程和启动时间未变化，不需要重启即可恢复。短测不能排除长期内存增长、其他数据规模或更复杂路线造成的新问题。

## 建议处理顺序（本轮未实施）

1. 将旗舰寻路及必要的前处理移到有上限的计算线程池或独立计算服务，避免阻塞页面／普通接口的执行线程。只把函数标记为 `async` 不能隔离同步 CPU 工作。
2. 增加全局计算并发上限、有限排队、明确排队超时／繁忙提示，并限制同一用户的重复任务；避免以无限队列掩盖过载。取消页面请求时还需考虑服务端计算是否能停止。
3. 再评估目录／图的版本缓存和重复计算复用；必须把舰船、技能、点位、开关以及星图／入侵快照版本纳入有效性，不能复用过期安全判断。
4. 修改后用相同负载复测：不仅看旗舰自己的耗时，还要保证首页、普通导航和 LP 接口的隔离效果。之后再补更长时间、实际目标部署机器上的测试。
